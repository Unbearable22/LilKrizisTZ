Доработка пользователя: неполные исходные данные больше не являются обязательной остановкой. Понятная задача выполняется сразу; индивидуальный разбор возвращает partial_answer с условными вариантами и необязательными уточнениями. Отсутствие нормативных оснований по-прежнему останавливает соответствующую часть. Это заменяет прежнее требование полной анкеты. Актуальное описание: docs/conditional-answers.md.

# Юридическая помощь через MCP и локальные файлы

Дата: 20.10.2026. Статус: проект спецификации для проверки пользователем, реализация ещё не начата.

## Цель и согласованные решения

Пользователь пишет юридический вопрос обычным языком. Система сама определяет задачу, получает через MCP соответствующий мастер-промпт и подходящие нормативные фрагменты, передаёт модели исходный вопрос вместе с контекстом и возвращает ответ без отображения источников.

Согласованная цепочка:

**Сообщение в веб-чате → классификация задач → получение промпта через MCP → поиск и чтение нормативных фрагментов через MCP → исходный вопрос вместе с контекстом передаётся модели → ответ без отображения источников.**

Для первого прогона согласованы одна поддерживаемая задача `legal_help` («Юридическая помощь»), один мастер-промпт `.txt` и локальные нормативные файлы `.md`. НСПД, Госуслуги, автоматическое скачивание законов и другие внешние инструменты не входят в этот этап. Запросы к выбранной LLM остаются необходимой частью цепочки; «только локальные файлы» ограничивает источники MCP, а не требует локальной модели.

Пользователь подтвердил автономный выбор алгоритма. Автономность на первом этапе означает отсутствие ручного выбора задачи, документов и фрагментов. Она не включает изменение дел, подачу заявлений, оплату услуг или произвольное выполнение команд.

## Текущее состояние проекта

Основной интерфейс по решению пользователя — веб-чат `groundAndLaw`, добавленный в ветку main на GitHub. Изучены `index.html`, `script.js` и `db.js`: реализованы создание/переключение/удаление чатов, сообщения и вложения, локальная история IndexedDB. Запросов к серверу модели пока нет; кнопки записи голоса не подключены. В текущем локальном checkout папка ещё не синхронизирована.

Существующий Python-проект содержит расчёты и Telegram-сценарии. `Integrations.explain` поясняет результат расчёта, но не выполняет предлагаемую цепочку. `Service.legal_search` ищет загруженные выдержки в SQLite; это не MCP и не файловая нормативная база.

Новый сценарий связывает существующий веб-интерфейс с серверным оркестратором через HTTP API. MCP-клиент и ключи LLM находятся на сервере, а не в браузере. Telegram не является целевым интерфейсом этой разработки; удалять старый код без отдельной необходимости не требуется. Расчёты и прежние данные не переносятся автоматически в веб-чаты.

## Архитектура и ответственность

| Компонент | Ответственность |
|---|---|
| Веб-чат groundAndLaw/локальный запуск | Принять вопрос, показать ответ и состояние выполнения |
| Оркестратор — приложение-хост | Сохранить исходный текст, вызвать классификатор, проверить результат, последовательно вызвать MCP, собрать контекст, вызвать модель и проверить структуру ответа |
| Классификатор LLM | Выдать структурированный список задач и недостающих сведений, не отвечая на юридический вопрос |
| MCP-клиент | Установить соединение с локальным сервером и выполнять разрешённые вызовы |
| MCP-сервер | Предоставить мастер-промпт, поиск по локальным нормативным фрагментам и чтение выбранных фрагментов |
| Исполнитель LLM | Подготовить структурированный ответ только на основе предоставленных материалов |
| Проверка результата | Проверить формат, допустимость идентификаторов источников и наличие обязательных разделов; не объявлять юридическую достоверность доказанной |

MCP-сервер запускается локальным отдельным процессом через stdio. Сетевой публичный сервер, OAuth MCP и отдельный домен не требуются. Сервер получает необходимые параметры вызовов, а не полную историю чатов. Секреты LLM остаются у приложения-хоста.

Используется реальное MCP-взаимодействие с согласованием возможностей, а не обычная Python-функция, названная MCP. Конкретные зависимости и совместимые версии фиксируются в плане реализации после проверки документации и среды.

## Локальные данные

Предлагаемая структура:

```text
knowledge/
  tasks.json
  prompts/
    legal_help.txt
  laws/
    manifest.json
    <document-id>.md
```

`tasks.json` содержит разрешённые идентификаторы задач, их описание и соответствие промптам. Первая версия содержит только `legal_help`. Около 20 задач из общей схемы не придумываются и не считаются реализованными.

`manifest.json` хранит для каждого документа: устойчивый ID, относительный путь `.md`, название, официальный URL источника, редакцию, территорию применения, период применимости (если установлен), дату проверки, срок подтверждённой актуальности, проверяющего и отметку учебных данных. Неизвестный срок действия нельзя заменять вымышленной датой. Отдельно задаётся срок подтверждённой актуальности для использования в поиске.

Документы делятся по заголовкам статей/пунктов. Длинные разделы разбиваются на ограниченные по размеру фрагменты с сохранением родительского заголовка. Каждый фрагмент имеет ID, ID документа, заголовок/пункт, текст и хеш содержимого. Точное деление на чанки и пределы объёма фиксируются в плане и тестах.

Неполные, просроченные или не подтверждённые материалы не используются как действующие правовые основания. Учебные файлы разрешены только в явно обозначенном демонстрационном режиме; ответ при этом не называется юридическим заключением.

## Интерфейсы MCP

1. **Получение промпта:** стандартная возможность MCP prompts, шаблон `legal_help`, содержимое из одного `.txt`. Отсутствие файла — явная ошибка, без подмены придуманным промптом.
2. **`search_legal_fragments`:** запрос и при необходимости территория/дата; возвращает ограниченный список идентификаторов фрагментов, заголовков, редакций и признаков применимости. Первая реализация использует локальный лексический поиск; достаточность поиска проверяется примерами. Векторная база на этом этапе не обязательна.
3. **`read_legal_fragment`:** чтение найденного фрагмента по ID; возвращает текст, ссылку, редакцию, статью/пункт и хеш. Путь файла от модели не принимается.

Сервер читает только выделенные каталоги. Запись, удаление, выполнение команд, сетевые запросы и чтение `.env`, файлов дел или произвольных путей отсутствуют. Переходы `..`, абсолютные пути и symlink за пределы каталога отвергаются.

## Обработка запроса

1. Принимается вопрос; оригинальный текст сохраняется неизменным отдельно от поисковых формулировок.
2. Классификатор возвращает список элементов `{task_id, formulation}` и результат `ready`, `needs_clarification` или `unsupported`. Ответ проверяется по схеме и каталогу разрешённых задач.
3. Запрос без понятной задачи вызывает уточнение. Запрос вне каталога не направляется в случайный алгоритм.
4. Несколько тезисов одной поддерживаемой задачи выполняются последовательно с удалением повторов; исходный вопрос остаётся контекстом для каждого тезиса. Задачи вне первой поддерживаемой области явно перечисляются как невыполненные. Если они необходимы для ответа на поддерживаемую часть, возвращается необходимость уточнения, а не видимость полного выполнения.
5. Для готовой задачи оркестратор получает `legal_help` через MCP, выполняет поиск и читает выбранные фрагменты.
6. Контекст ограничивается по объёму. При превышении лимита уменьшается число фрагментов целиком; нельзя незаметно обрезать часть нормы и представлять её как полный текст. В результате указывается ограниченность выбранного контекста.
7. Исполнитель получает системные инструкции, мастер-промпт, исходный вопрос, тезис задачи и нормативные фрагменты с ID. Текст вопроса и нормативных файлов рассматривается как данные, а не дополнительные управляющие инструкции.
8. Исполнитель возвращает внутренний результат с тезисами, идентификаторами использованного контекста, недостающими сведениями и ограничениями. Оркестратор проверяет структуру и происхождение контекста. Веб-чату передаётся ответ без списка документов, названий актов, редакций, номеров статей, ссылок, сносок и идентификаторов фрагментов. Эти сведения не включаются и в текст ответа.
9. Если основания не найдены, возвращается `insufficient_sources` без юридического ответа по памяти модели. При неполных основаниях возможен только явно ограниченный ответ со списком неподтверждённых частей.

Один запрос не запускает бесконечный агентный цикл. Количество задач, MCP-вызовов и попыток LLM ограничивается конфигурацией; отмена/ошибка прекращает обработку. Для первого прогона автоматически редактировать нормативную базу или карточку дела нельзя.

## Формат результата и ошибки

Пользовательский результат содержит:

- `status`: `answered`, `needs_clarification`, `unsupported`, `insufficient_sources` или `error`;
- исходный вопрос и выделенные задачи;
- краткий ответ и обоснование по каждой выполненной задаче;
- недостающие сведения и ограничения результата.

Неизвестные ID, вымышленные ссылки, невалидный формат ответа или сбой проверки не выдаются как успешный результат. Пользователь получает понятную ошибку без токенов и технических трассировок. Проверка ID подтверждает происхождение цитируемого материала, но не доказывает, что вывод юридически следует из него; полноценная экспертная оценка остаётся отдельной работой.

Сбои модели, MCP, отсутствие промпта, пустая база и недопустимая редакция различаются диагностикой. В журналах — идентификатор запуска, этап, выбранные ID и хеши; полные сообщения пользователей и секреты не записываются автоматически. Политика длительного хранения юридических диалогов не расширяется этим этапом.

## Веб-чат и воспроизводимый прогон

Пользователь вводит вопрос в существующий `groundAndLaw`. Веб-чат отправляет исходное сообщение серверу, показывает ожидание, затем ответ без источников и ссылок. Классификация и подбор контекста происходят автоматически. Ошибка сервера или модели отображается явно, не как успешный ответ. Исходное сообщение сохраняется для повторной попытки; возврат ответа связан с исходным чатом, даже если пользователь переключился в другой.

Браузер не обращается напрямую к LLM или локальной файловой системе MCP. Мастер-промпты, нормативные материалы и ключи остаются на сервере. Пользовательские вложения отделяются от доверенной нормативной базы и не становятся правовым основанием автоматически. Пока их обработка не реализована, интерфейс явно сообщает, что вложение не проанализировано.

Локальная история в IndexedDB уже существует. Личные аккаунты, серверная синхронизация истории и привязка к прежним делам не согласованы и не считаются включёнными в первый прогон. Перед публичным размещением требуется отдельно выбрать механизм ограничения доступа; административный API-токен нельзя публиковать в JavaScript. Первый технический прогон ограничивается локальным/закрытым контуром.

Для воспроизводимого тестирования предусматривается локальный запуск той же серверной цепочки с выводом промежуточных этапов. Диагностика отделена от обычного ответа в веб-чате. Каждый новый вопрос обрабатывается как самостоятельный запрос; передача истории диалога модели требует отдельного согласования и не подразумевается наличием сохранённого чата.

Модель и доступы не выбираются без конфигурации оператора. Без настроенной модели возвращается понятное сообщение о невозможности реального запуска. Тестовый режим с подставными ответами явно отделяется от настоящего вызова LLM.

## Проверка и критерии приёмки

Автотесты должны подтвердить:

1. Сохранение исходного вопроса и проверку классификации по каталогу.
2. Несколько тезисов, неизвестную задачу, неоднозначность и отсутствие источников.
3. Реальное соединение MCP-клиента и сервера отдельным процессом, получение промпта, поиск и чтение фрагмента.
4. Запрет произвольных путей, symlink-выхода и записи через MCP.
5. Чанки с прослеживаемой редакцией/пунктом, устаревшие материалы и демонстрационный режим.
6. Сохранение границ контекста, отсутствие бесконечного цикла и корректные ошибки внешней модели.
7. Невозможность принять несуществующий источник как проверенный.
8. Отправку вопроса из веб-чата, состояния ожидания/ошибки, повторную попытку, отсутствие источников в тексте и публичном API и привязку ответа к исходному чату при переключении. Существующие функции веб-интерфейса должны сохраняться.

Первая демонстрация показывает все промежуточные этапы на небольшом помеченном комплекте документов, включая отрицательные случаи. Живой прогон отдельно подтверждает получение ответа от настроенного провайдера. Юридическая приёмка на реальных действующих актах требует их подготовки и проверки специалистом; она не заменяется тестами синтетических данных.

Спецификация отражает согласованный пользователем поток. Предложенные подробности (локальный stdio, метаданные, HTTP API веб-чата, границы памяти, проверки и поиск) включены в документ для отдельного рассмотрения пользователем, а не считаются заранее одобренными.

## Уточнения для первого прототипа — 21.10.2026

Этот раздел заменяет противоречащие ему предположения раннего проекта спецификации. Пользователь попросил перейти к реализации первого прототипа после согласования цепочки.

- Одна функция — отдельный MCP. Первый реестр содержит только `legal_help`, закреплённый за локальным MCP юридической помощи. Сборка контекста этого MCP включает получение `.txt` и поиск/чтение `.md`.
- До выполнения стоят серверная проверка формы входа, классификатор LLM и программный валидатор его плана. Модель возвращает только разрешённый function_id, не адрес сервера или путь.
- По первоначальному сообщению определяется полный список недостающих сведений. Он показывается единой анкетой до запуска MCP. Для общей правовой справки нужны описание ситуации и цель; для анализа конкретного участка дополнительно регион/муниципалитет, адрес, номер либо координаты, права, категория/ВРИ и исходные документы. Неизвестные сведения пользователь отмечает явно; конкретное заключение при этом не выдаётся. Внешняя проверка адреса и получение данных НСПД отложены.
- Источники прототипа — небольшой явно учебный набор, не база действующих законов. Режим demo проверяет реальный MCP отдельным процессом, но использует детерминированный демонстрационный обработчик вместо LLM. Интерфейс постоянно показывает режим. Режим live использует настроенную OpenAI-совместимую LLM для классификации и ответа; без конфигурации запуск live невозможен, скрытого переключения на demo нет.
- Сервер prototype слушает 127.0.0.1, обслуживает существующие файлы groundAndLaw и узкий `/api/legal-help`. Административный API не используется. Это локальный показ без публичных аккаунтов; перед публичной эксплуатацией требуется отдельный контроль доступа. Запросы API ограничены размером/конкурентностью, проверяется Origin при его наличии. Секреты не уходят в JavaScript или MCP-процесс.
- Веб-чат сохраняет историю локально. API принимает текст текущего вопроса и отдельный объект анкеты; ответы относятся к исходному chatId. Пользовательские вложения пока не анализируются, об этом сообщается до запуска; они не становятся источниками нормативной базы.
- Вопрос не переформулируется в исходных данных исполнителя. Известные на первом этапе источники идентифицируются по ID, редакции и хешу; эти данные используются только внутри сервера для проверки контекста. Неизвестные идентификаторы модели отклоняются. Проверка происхождения фрагмента не доказывает юридическую правильность вывода. Финальный ответ не содержит источников.
- Для прототипа: вопрос до 8000 символов, JSON-тело до 64 КиБ, до 4 задач, не более 6 выбранных фрагментов по 4000 символов, MCP-контекст до 16000 символов, максимум один классификационный и один исполнительский запрос на задачу без автоматических повторов. Внешние вызовы имеют таймауты. Эти пределы являются настройкой первого прогона, а не юридическим правилом.
- Изменения выполняются в текущем рабочем каталоге с сохранением накопленных незакоммиченных файлов. Коммиты/публикация не выполняются автоматически: прежнее решение пользователя остановить коммит сохраняется.

## Доработка плана: источники не отображаются — 21.10.2026

По решению пользователя источники нигде не показываются клиенту: ни в сообщениях, ни в отдельных блоках, ни в истории чата, ни в выдаваемых браузеру данных API. Убираются также ссылки, сноски, названия документов, номера статей и идентификаторы фрагментов в тексте ответа. Технический trace с метаданными контекста остаётся на сервере.

Нормативные файлы, поиск и чтение через MCP сохраняются как внутренний механизм подготовки ответа. Отсутствие достаточного контекста по-прежнему прекращает подготовку юридического ответа; скрытие источников не разрешает отвечать по памяти модели. Недостающие сведения и ограничения ответа остаются видимыми.

Это изменение требований; существующий код прототипа ещё выводит источники. Его адаптация и повторная проверка отмечены отдельной невыполненной задачей в плане реализации.

## Согласованное правило эталонов — 21.10.2026

Основной эталон нормативного текста — «КонсультантПлюс» (consultant.ru). «Гарант» используется для дополнительной сверки. При расхождении всегда выбирается вариант «КонсультантПлюс» для той же даты применения нормы; само расхождение не требует ручного выбора сервиса. Сведения о различии фиксируются во внутреннем журнале.

Сопоставляются один и тот же акт, структурная единица и редакция, действующая на дату вопроса. Будущая редакция не подменяет действующую. Если нужный текст «КонсультантПлюс» недоступен или дата его применения не установлена, проверка не считается завершённой; ответ по памяти модели не заменяет отсутствующий текст. Официальные публикации и прежний аудит сохраняются как дополнительное подтверждение и история проверки, а не как обязательное условие выбора между двумя согласованными эталонами.

Это правило заменяет ранее предложенный приоритет официальной консолидированной выгрузки как рабочего эталона. Предыдущие разделы об официальной сверке описывают исторические результаты. Полная постатейная сверка пяти актов по «КонсультантПлюс» и «Гаранту» завершена 21.10.2026; результат — knowledge/reference-audit-summary.json. Установление приоритета не подтверждает автоматически качество уже загруженных текстов и не продлевает срок их проверки.

Ссылки, реквизиты проверки и журнал расхождений остаются внутренними. Правило описано в документации; механизм автообновления пока не реализован.
