# Исследование таймаутов — 21.10.2026

## Методика

Последовательно, без повторов, отправлены четыре прямых API-запроса. Для каждой модели использованы одинаковые сообщения, температура, JSON-режим и лимит вывода. Первый запрос просит JSON из одного поля, второй — юридический ответ с одинаковым сохранённым нормативным контекстом. В замерах не участвуют веб-чат, классификатор и время поиска MCP. Подключение и TLS измерены через события HTTP-клиента; заголовки авторизации и текст запросов в отчёт не включены.

Диагностический лимит ожидания увеличен до 90 секунд только для измерения. Рабочие таймауты приложения не увеличивались. Использовались тот же ключ, endpoint и среда, что и в приложении; прокси-переменные не установлены.

Все четыре ответа HTTP 200. В каждом случае почти всё время прошло после отправки тела запроса до получения заголовков ответа. Тело ответа получено практически сразу после заголовков. Flash на юридическом запросе прошёл текущую проверку формата, внутренних подтверждений и отсутствия источников.

## Что установлено

Задержка воспроизводится на пути обслуживания `deepseek-v4-pro` через Tooken Club даже без нормативного контекста. Сетевое соединение/TLS и MCP не объясняют десятки секунд ожидания. Порог классификации 45 секунд меньше наблюдавшегося времени даже короткого запроса Pro; порог юридического ответа 60 секунд близок к 58,3 секунды в замере. Этим объясняется чувствительность приложения к колебаниям задержки этого модельного маршрута.

Нельзя по этим данным установить, какая часть ожидания приходится на очередь, внутреннюю маршрутизацию и выполнение самой модели. Также нельзя гарантировать, что Flash никогда не будет ограничен или замедлен. Одна пара замеров на профиль не является статистическим SLA. Сжатие контекста не устраняет основную наблюдавшуюся задержку Pro: короткий запрос уже занял 49 секунд.

## Исправление

Проверена конфигурация Flash для обоих этапов на 20 синтетических сценариях через реальный HTTP/MCP: **20/20 автоматических ожиданий, без таймаутов и HTTP 429**. В локальной `.env` установлены `LLM_MODEL=deepseek-v4.1-flash` и `LLM_CLASSIFIER_MODEL=deepseek-v4.1-flash`. Ключ и рабочие таймауты сохранены. После изменения необходимо перезапустить уже работающий веб-сервер. Модель Pro остаётся доступной настройкой, автоматического переключения после ошибки и повторного списания нет. Контекст, нормы, проверка внутренних ID и запрет источников сохраняются. Выбор более быстрого маршрута устраняет наблюдаемое узкое место приложения; внутренний сбой провайдера этим не исправляется.

## Повторная диагностика

```bash
.venv/bin/python scripts/diagnose_llm.py --live
```

Команда делает платные запросы последовательно, останавливается при 429 и сохраняет только метрики в `data/llm-diagnostics/report.json`. Названия моделей можно передать через `--models`, общий предел одного диагностического запроса — `--timeout`. При просроченной базе возможен только короткий профиль без нормативного контекста. Приватные ответы первоначального исследования остаются под игнорируемым `data/timeout-study/` и не включаются в клиентский архив.


В контрольном прогоне выполнено 36 вызовов модели. Медиана времени содержательного ответа всей цепочки — 14.5 секунды, максимум — 31.77 секунды (составной вопрос). Это измерения данного прогона, не гарантия доступности. Автоматические проверки не заменяют юридическую экспертизу. При повторной диагностике контекст заново подбирается MCP; численные результаты могут отличаться.
