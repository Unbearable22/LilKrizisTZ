# Продолжение диагностики LLM — 02.11.2026

Текущая версия проекта отправлена на origin/main, исходная точка продолжения — f75704e. Проверка не отключалась; общий предел запроса остаётся 120 секунд. Размещение на сервере не выполнялось.

## Что установлено

Потоковый диагностический вызов получает HTTP 200 и заголовки быстро, но может не выдать ни одного события с текстом до ограничения 30 секунд. Это отделяет установление соединения от ожидания полезного ответа; по одному такому измерению нельзя разделить очередь и вычисление модели. Простое включение streaming не устраняет ожидание.

На одном и том же сохранённом земельном контексте (30 908 символов) получены последовательные пробы: без reasoning_effort — таймаут 30,015 с без текста; low — завершение за 23,964 с; повтор low — за 3,764 с. Вердикты двух успешных проб различались. Параметр принят API для gpt-6-luna, но это не доказательство единообразной обработки всех маршрутов или сопоставимого качества. [Точные request ID и команда диагностики](provider-timeout-support.md) подготовлены для ручного обращения к провайдеру; ничего в поддержку не отправлялось.

Добавлена необязательная LLM_VERIFIER_REASONING_EFFORT (пустое значение / low / medium / high). Пустое значение ничего не отправляет и сохраняет прежний режим. Параметр действует только на проверяющую модель; генерация и классификация не меняются. Совместимость конкретного значения зависит от API и модели; в живых пробах проверен только low с gpt-6-luna. Автоматического повтора без параметра при отказе провайдера нет.

## Исправлен подтверждённый дефект ссылок

В ответе по наследству модель вернула 40-символьный ID вместо существующего 39-символьного: лишний символ в хеше. Сервер правильно отклонил его как invalid_citations. Для генерации, стилистической правки и содержательного исправления теперь передаются короткие номера прочитанных фрагментов, как уже делалось на этапе проверки. Хост восстанавливает настоящие ID только в полях citations, evidence_ids и fragment_id. Вопрос, текст ответа, условия и дословные цитаты не переписываются.

Неизвестный номер не подбирается по похожести и не становится действительной ссылкой; он остаётся ошибкой проверки. Это устраняет необходимость копировать длинные хеши моделью, но не гарантирует отсутствие любых неверных ссылок и не решает таймауты API.

Целевые проверки сначала воспроизвели отсутствие преобразования, затем прошли: короткие ID в ответе/обоих типах исправления; неизменность исходного вопроса и цитат; восстановление вложенных ссылок; неизвестный номер остаётся неизвестным. Новые параметры проверены на отсутствие влияния на классификатор/генератор и на отклонение недопустимой настройки до сетевого обращения.

## Дополнительная проверка после коротких ID

Единственный повтор наследственного вопроса с короткими ID: **partial_answer, 23.47 с, 3 вызова модели**. Использованы gpt-6-luna на всех стадиях и режим reasoning провайдера по умолчанию (без low). Неизвестных ID нет; ответ прошёл обязательную смысловую и структурную проверки, сохранены ссылки на прочитанные документы. Это подтверждение конкретного пути после исправления, а не новый успешный прогон всех семи тем или доказательство юридической правильности. Полная неудачная таблица выше сохранена.

## Автоматическая проверка и дальнейшая граница

Полный Python unittest после всех изменений: **190/190**, 37,736 с. JavaScript: **20/20**. Интерфейс не менялся; браузерные сценарии предыдущей версии остаются отдельной проверкой UI, а не доказательством работоспособности внешнего LLM API.

Добавлен scripts/diagnose_verifier.py: ровно один явно разрешённый платный потоковый вызов по однозадачному синтетическому QA-файлу, до 30 секунд. Сохраняются только времена, числовой usage, размер и безопасный request ID. Тексты вопроса, ответа и reasoning не попадают в результат. Неполный поток не считается завершённым вердиктом. Результат диагностики не используется для публикации ответа в чате. Существующий файл метрик не перезаписывается.

Остающееся ограничение: время обслуживания внешним API нестабильно на нескольких стадиях. Дальнейшая серия случайных смен моделей или скрытое увеличение таймаутов не обоснованы. Для следующего решения нужны сведения провайдера по request ID и отдельное сравнение качества проверяющего маршрута. Возможный переход к фоновой обработке потребует нового решения о времени ожидания и интерфейсе; в этой версии он не реализован.
