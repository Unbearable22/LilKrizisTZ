# Повышение качества юридического прототипа — 21.10.2026

## Брейншторм и выбранный вариант

Цель — исправить семь проваленных сценариев существующего веб-чата, сохранив отдельный файловый MCP, исходный вопрос и внутреннюю проверку подтверждений. Источники клиенту не показываются. Новые внешние сервисы и автоматическая подача документов не добавляются.

Рассмотрены три подхода:

1. Увеличить таймаут и ослабить фильтр. Быстро, но не исправляет выбор неподходящих норм.
2. Улучшить сбор контекста по статьям, диагностику и проверку изложения. Выбран для текущего изменения: причины подтверждены предыдущим прогоном, новая инфраструктура не нужна.
3. Добавить векторный поиск и отдельную модель для проверки правовых выводов. Может улучшить поиск по смыслу, но требует отдельной оценки полноты, стоимости, задержек и ошибок проверяющей модели. Отложено.

## Внесённые изменения

Поиск сначала ранжирует материал, затем собирает контекст с учётом статьи. У основной статьи резервируются первые два фрагмента, оставшиеся места занимают релевантные фрагменты. Порядок внутри статьи сохраняется. Добавлено небольшое расширение поисковой лексики для прав на документы товарищества и участия в расходах без членства. Эти правила меняют поиск, а не содержат юридические ответы или номера нужных статей.

Лимиты остаются: до шести фрагментов, до 16 тысяч символов нормативного текста. Фрагменты не обрезаются по оставшемуся месту. Начало длинной статьи не означает полного покрытия: пропущенные части и ограничения контекста учитываются как прежде.

Предусмотрена отдельная настройка `LLM_CLASSIFIER_MODEL`: если она пуста, классификатор использует `LLM_MODEL`; исполнитель всегда использует `LLM_MODEL`. Выбор быстрой модели проверяется отдельно, не меняя модель юридического ответа.

Обычные выражения «предусмотрено федеральным законом» допускаются. Названия конкретных актов, номера, даты-реквизиты, ссылки, сноски и внутренние ID по-прежнему блокируются. Проверки Python и JavaScript согласованы.

Если готовый ответ содержит реквизиты, допускается одна дополнительная попытка изменить изложение с тем же вопросом и контекстом. Её результат заново проверяется: формат, статус, допустимые ID, ограничения и отсутствие источников. Повторное нарушение останавливает обработку. Такая попытка расходует ещё один запрос модели и не гарантирует сохранение юридического смысла; экспертная проверка остаётся необходимой.

Ошибки модели разделены на таймаут, соединение, авторизацию, ограничение частоты, HTTP-ошибку, некорректный JSON, обрезанный или чрезмерный ответ. Внутренняя диагностика содержит ID запуска, этап, код, время и при наличии HTTP-статус. Тексты запросов, ответы провайдера, ключи и трассировки не добавляются в пользовательский результат или диагностический журнал.

Классификация получает меньший лимит выходных токенов. Отдельно задаются `LLM_CLASSIFY_TIMEOUT` (45 секунд) и `LLM_ANSWER_TIMEOUT` (60 секунд); допустимый диапазон 5–90. Общий бюджет цепочки остаётся 120 секунд, поэтому длинный составной запрос или переформулирование могут быть остановлены общим лимитом. Автоматических повторов после сетевой ошибки нет.

## Критерии проверки

- Семь прежних провалов повторяются через HTTP, реальную модель и настоящий stdio MCP.
- Отдельно проверяется получение начала длинной процедуры.
- Общие упоминания законодательства допускаются, конкретные реквизиты блокируются.
- Переформулирование не принимает вымышленные ID и не зацикливается.
- Внутренняя причина ошибки не попадает в публичный ответ.
- Весь набор проверок и браузерный сценарий выполняются повторно.

## Дальнейшее улучшение

Следующий самостоятельный этап — набор вопросов заказчика с экспертными эталонами: обязательные условия, допустимые выводы, исключения и случаи отказа. На нём следует сравнить текущий поиск с гибридным и измерить полноту найденных норм. Только после этого имеет смысл добавлять модель-проверяющего или менять модели по этапам. Успешный статус API сам по себе не является оценкой юридической правильности.

Автообновление и срок подтверждённой актуальности документов данным изменением не затрагиваются. Просроченные материалы не допускаются к ответу.

## Контроль провайдера при оценке

Реальный повтор выявил HTTP 429 помимо таймаутов. Поэтому инструмент оценки переведён в последовательный режим. После первого ограничения частоты или трёх последовательных таймаутов оставшиеся вопросы получают `not_run` с причиной, а не фиктивный результат или автоматический повтор. Первая серия из семи проблемных вопросов дала два содержательных ответа; остальные остановлены из-за таймаутов/429. Пробная пара вопросов с отдельным классификатором также попала под 429. Это не доказывает ни качество, ни непригодность быстрой модели; выбранная модель в `.env` не менялась. Затем запущен отдельный последовательный прогон.
